# Мотивация

После открытия партнёрского API текущих данных Яндекс Метрики недостаточно: они показывают поведение пользователей сайта, но не позволяют увидеть состояние API, очередей, баз данных и фонового расчёта цены. Из-за этого команда узнаёт о зависших и потерянных заказах от клиентов, а причины медленной работы MES ищет вручную.

Технический мониторинг нужен, чтобы:

- обнаруживать сбои раньше клиентов и быстро определять проблемный компонент;
- видеть, теряются ли сообщения между MES и CRM и успевают ли потребители разбирать очередь;
- отличать нехватку ресурсов от ошибок приложения или медленных запросов к базе данных;
- оценивать влияние партнёрской нагрузки на Shop API, CRM API и MES API;
- планировать увеличение ресурсов до того, как единственный экземпляр приложения или базы данных станет узким местом.

Бизнес-мониторинг нужен, чтобы контролировать прохождение заказа по всем этапам. Он позволит находить заказы, которые слишком долго находятся в одном статусе, измерять фактический срок выполнения и снижать число потерянных заказов, просрочек, обращений в поддержку и расторгнутых контрактов.

# Выбор подхода к мониторингу

Для Shop API, CRM API и MES API применяется подход RED:

- **Rate** — интенсивность запросов;
- **Errors** — доля ошибочных ответов;
- **Duration** — время ответа.

RED хорошо подходит для пользовательских и партнёрских API: он отвечает на вопросы, доступен ли сервис, справляется ли он с нагрузкой и получают ли клиенты корректный ответ.

Для экземпляров приложений, PostgreSQL и хранилища применяется подход USE:

- **Utilization** — доля занятого ресурса;
- **Saturation** — объём работы, ожидающей свободного ресурса;
- **Errors** — ошибки ресурса.

USE помогает найти инфраструктурное узкое место. Это особенно важно, поскольку у каждого приложения и каждой базы данных только один экземпляр и запас отказоустойчивости отсутствует.

RabbitMQ и прохождение заказа контролируются отдельными техническими и бизнес-метриками. Одних HTTP-метрик недостаточно: API может успешно принять заказ, после чего сообщение останется в очереди, попадёт в DLX или не будет обработано.

Во всех метриках используются только ограниченные наборы labels. `user_id`, `order_id`, имя файла, URL с параметрами и другие уникальные значения в labels не добавляются: они создают высокую кардинальность и резко увеличивают объём и стоимость хранения временных рядов. Идентификаторы заказа и пользователя должны находиться в логах и трассировках.

## Метрики API

Метрики собираются для Shop API, CRM API и MES API.

### RPS

Счётчик запросов и рассчитанный по нему RPS показывают текущую нагрузку, её рост и распределение между сервисами и операциями. Метрика помогает сопоставить ухудшение работы с открытием партнёрского API и определить часы пик.

Labels: `service` (`shop`, `crm`, `mes`), `environment`, `route` в виде шаблона маршрута, `method`, `client_type` (`web`, `partner`, `internal`). Название партнёра и идентификатор пользователя не используются.

### Время ответа p50, p95 и p99

Гистограмма длительности HTTP-запросов показывает обычное время ответа через p50, опыт большинства медленных клиентов через p95 и редкие тяжёлые случаи через p99. Среднего значения недостаточно: несколько очень долгих запросов MES могут быть незаметны на фоне быстрых запросов. Длительный расчёт цены измеряется отдельно, поэтому HTTP-запрос на запуск расчёта не должен оставаться открытым до его завершения.

Labels: `service`, `environment`, `route`, `method`, `status_class` (`2xx`, `4xx`, `5xx`).

### Ответы HTTP 2xx, 4xx и 5xx

Счётчики ответов по классам нужны для расчёта доли успешных и ошибочных запросов. Рост 4xx может означать некорректный контракт партнёрского API, превышение лимитов или ошибки клиентов. Рост 5xx означает проблему сервиса или его зависимостей. Группа 2xx показывает успешно обслуженную нагрузку.

Labels: `service`, `environment`, `route`, `method`, `status_class`. Конкретный код ответа можно хранить как label, если набор кодов ограничен.

### Активные запросы

Число одновременно обрабатываемых запросов показывает насыщение пула потоков и помогает объяснить рост latency ещё до появления 5xx.

Labels: `service`, `environment`.

## Метрики экземпляров приложений

### CPU

Использование CPU для Shop API, CRM API и MES API показывает, хватает ли вычислительных ресурсов единственному экземпляру. Стабильно высокий CPU вместе с ростом очереди выполнения и latency указывает на насыщение.

Labels: `service`, `environment`, `instance`.

### Память

Использование памяти в байтах и процентах, а также для Java — heap, non-heap, паузы GC; для .NET — managed heap и паузы GC. Метрики позволяют обнаружить утечку памяти, частые сборки мусора и риск завершения процесса по нехватке памяти.

Labels: `service`, `environment`, `instance`, а для областей памяти — `area` или `generation` с ограниченным набором значений.

### Насыщение приложения

Контролируются длина очереди пула потоков, число занятых потоков, размер пула соединений к БД и число ожидающих соединение запросов. Эти показатели объясняют рост времени ответа даже при умеренном CPU.

Labels: `service`, `environment`, `instance`, `pool`.

## Метрики PostgreSQL Shop и MES

### Соединения с БД

Количество активных и ожидающих соединений и их доля от `max_connections` показывают, близка ли база к исчерпанию лимита. Отдельно отслеживается насыщение пула соединений каждого приложения.

Labels: `database` (`shop`, `mes`), `environment`, `state` (`active`, `idle`, `waiting`), `application`.

### Размер БД

Общий размер базы, размер таблиц и индексов и скорость роста нужны для планирования диска и поиска быстро растущих сущностей. Для MES рост таблиц заказов может быть связан с медленным дашбордом.

Labels: `database`, `environment`, `relation` только для заранее выбранного ограниченного списка крупных таблиц и индексов. Динамические имена и идентификаторы не используются.

### Задержка запросов

Отслеживаются p50, p95 и p99 времени выполнения запросов, число медленных запросов, время ожидания блокировок и доля попаданий в буферный кеш. Метрики позволяют проверить, связан ли медленный MES-дашборд с запросом к БД, блокировками или чтением с диска.

Labels: `database`, `environment`, `operation` (`select`, `insert`, `update`, `delete`), `query_name` для небольшого заранее заданного набора нормализованных запросов. Полный SQL и параметры в labels не помещаются.

### Ресурсы и ошибки БД

Контролируются CPU, память, заполнение диска, IOPS, задержка чтения и записи, число deadlock, ошибки соединения и число ожидающих блокировок. Это покрывает utilization, saturation и errors по USE.

Labels: `database`, `environment`, `operation` или `error_type`, где применимо.

## Метрики RabbitMQ

Метрики собираются отдельно по очередям интеграции MES и CRM.

### Сообщения ready

Число сообщений, готовых к доставке потребителю, показывает накопившуюся очередь. Постоянный рост означает, что потребители не успевают за издателями или не работают.

Labels: `environment`, `vhost`, `queue`.

### Сообщения in-flight

Число доставленных, но ещё не подтверждённых сообщений показывает объём текущей обработки. Большое и долго не уменьшающееся значение может означать зависшие обработчики или слишком длинную обработку.

Labels: `environment`, `vhost`, `queue`.

### Сообщения в DLX

Количество сообщений в dead-letter exchange и скорость их поступления нужны для немедленного обнаружения сообщений, которые не удалось обработать. Именно здесь могут оказаться потерянные для бизнеса заказы.

Labels: `environment`, `vhost`, `source_queue`, `reason` с ограниченным набором причин.

### Повторные доставки

Скорость redelivery показывает сообщения, которые возвращаются в очередь после сбоя или отсутствия подтверждения. Рост метрики выявляет циклические ошибки обработки и нестабильных потребителей.

Labels: `environment`, `vhost`, `queue`.

### Consumer lag и возраст старейшего сообщения

Разница между опубликованными и обработанными сообщениями, а также возраст старейшего сообщения показывают реальную задержку обработки. Количество ready само по себе недостаточно: даже небольшая очередь может содержать старый зависший заказ.

Labels: `environment`, `vhost`, `queue`, `consumer_group` при наличии стабильных групп.

### Состояние потребителей и потоки сообщений

Отслеживаются число активных consumers, скорость publish, deliver и ack, а также ошибки соединений и каналов. Метрики помогают отличить всплеск входящего потока от остановки потребителя.

Labels: `environment`, `vhost`, `queue`; для соединений — `application`, но не случайное имя клиента.

## Метрики S3

### Размер хранилища и число объектов

Объём данных и число объектов с темпом роста нужны для прогноза затрат и контроля накопления 3D-моделей.

Labels: `environment`, `bucket`, `storage_class`.

### Ошибки операций

Счётчики ошибок чтения, записи и удаления позволяют обнаружить проблемы доступа, квот или сети, из-за которых заказ не сможет перейти к расчёту цены.

Labels: `environment`, `bucket`, `operation`, `status_class` или ограниченный `error_type`.

### Задержка операций

p50, p95 и p99 длительности загрузки и скачивания показывают влияние S3 на отправку файла и запуск расчёта.

Labels: `environment`, `bucket`, `operation`, `status_class`. Имя объекта и заказа не используются.

## Метрики расчёта цены

### Длительность расчёта

Гистограмма времени от постановки задачи на расчёт до результата измеряется отдельно от HTTP latency. Нормальный диапазон по текущим данным — от 2 до 30 минут. p50, p95 и p99 покажут деградацию и помогут оценить ожидание клиента.

Labels: `environment`, `result` (`success`, `failed`, `timeout`), `source` (`shop`, `partner`), `complexity_bucket` по заранее определённым диапазонам числа полигонов. Точное число полигонов и `order_id` не используются.

### Очередь расчётов

Количество ожидающих расчётов, число одновременно выполняемых расчётов и возраст старейшей задачи показывают насыщение вычислительного контура MES.

Labels: `environment`, `source`, `state` (`queued`, `running`).

### Результаты расчётов

Счётчики успешных, ошибочных и прерванных расчётов нужны для оценки надёжности процесса, а не только его скорости.

Labels: `environment`, `result`, `source`, `error_type` с ограниченным справочником.

## Метрики прохождения заказа

### Время заказа в статусе

Для каждого перехода измеряется время нахождения заказа в предыдущем статусе. Дополнительно считается текущее количество заказов в каждом статусе и возраст самого старого заказа. Это позволяет быстро увидеть этап, на котором образовался затор.

Labels: `environment`, `status`, `source` (`shop`, `partner`), `channel` (`b2c`, `b2b`). `order_id`, `user_id` и название партнёра не используются.

### Переходы между статусами

Счётчики успешных и ошибочных переходов показывают, сколько заказов движется по процессу и где нарушается ожидаемая последовательность.

Labels: `environment`, `from_status`, `to_status`, `result`, `source`.

### Сквозное время выполнения

Измеряется время от `SUBMITTED` до `PRICE_CALCULATED`, от `SUBMITTED` до `MANUFACTURING_STARTED` и от `SUBMITTED` до `CLOSED`. p50, p95 и p99 позволяют сравнить фактические сроки с обещанными тремя неделями.

Labels: `environment`, `stage`, `source`, `result`.

### Просроченные и потерянные заказы

Отслеживается число заказов, превысивших допустимое время в статусе, и число заказов, для которых нет ожидаемого следующего перехода. Эта метрика напрямую отражает главную проблему бизнеса.

Labels: `environment`, `status`, `source`, `severity`. Список конкретных заказов формируется отдельным запросом или отчётом, а не labels временного ряда.

## Показатели насыщенности, пороги и действия

Начальные пороги задаются как практически применимые ориентиры. После двух-четырёх недель сбора данных их нужно уточнить по базовой линии отдельно для рабочего времени, ночи и пиковых периодов. Короткий всплеск не должен создавать шум: предупреждения срабатывают при устойчивом превышении, а критические алерты — при угрозе потери заказов или недоступности.

- **API latency:** предупреждение, если p95 превышает 1 секунду 10 минут; критический алерт, если p95 выше 3 секунд или p99 выше 5 секунд 5 минут. Исключение — отдельная фоновая метрика расчёта цены. Действия: дежурный проверяет RPS, CPU, пулы и задержку БД; при подтверждённом инциденте ограничивается партнёрская нагрузка и создаётся задача на оптимизацию.
- **Ошибки API:** предупреждение при доле 5xx выше 1% за 10 минут и не менее 20 запросах; критический алерт при 5xx выше 5% за 5 минут. Рост 4xx выше 10% за 15 минут создаёт предупреждение для проверки контракта и лимитов партнёрского API. Действия: уведомление дежурному, проверка последнего релиза и зависимостей; при необходимости откат релиза.
- **CPU приложений:** предупреждение выше 70% 15 минут, критический алерт выше 90% 5 минут вместе с ростом latency или очереди потоков. Действия: анализ профиля нагрузки, временное ограничение внешнего трафика; затем увеличение ресурсов или числа экземпляров.
- **Память приложений:** предупреждение выше 80% лимита 15 минут, критический алерт выше 90% 5 минут либо при устойчивом росте после GC. Действия: проверка heap и GC, создание heap dump по безопасной процедуре, перезапуск только как временная мера, затем устранение утечки или увеличение лимита.
- **Пулы приложений:** предупреждение при занятости потоков или соединений выше 80% 10 минут; критический алерт выше 95% либо при наличии ожидающих запросов 5 минут. Действия: найти медленные операции, проверить БД и внешние зависимости, скорректировать размеры пулов только после устранения причины.
- **Соединения PostgreSQL:** предупреждение выше 70% `max_connections` 10 минут, критический алерт выше 85% 5 минут или при отказах подключения. Действия: найти утечки и долгие транзакции, ограничить пулы приложений; увеличение `max_connections` выполнять только после оценки памяти.
- **Диск PostgreSQL:** предупреждение при заполнении выше 75% или прогнозе исчерпания менее чем за 30 дней; критический алерт выше 85% или прогнозе менее 7 дней. Действия: расширить диск, проверить рост таблиц и индексов, настроить архивацию и очистку.
- **Задержка PostgreSQL:** предупреждение, если p95 основных запросов выше 500 мс 10 минут; критический алерт выше 2 секунд 5 минут. Для запроса MES-дашборда дополнительно ставится цель p95 не более 1 секунды. Действия: проверить план выполнения, индексы, блокировки, I/O и объём выборки.
- **Блокировки PostgreSQL:** предупреждение при ожидании блокировки дольше 5 секунд; критический алерт при ожидании дольше 30 секунд или любом deadlock. Действия: найти блокирующую транзакцию, связаться с владельцем сервиса, безопасно завершить её при угрозе простоя и исправить транзакционную логику.
- **RabbitMQ ready:** предупреждение, если очередь непрерывно растёт 10 минут или содержит больше 1 000 сообщений; критический алерт при количестве свыше 10 000 либо возрасте старейшего сообщения больше 5 минут. Действия: проверить consumers и их ошибки, остановить неконтролируемый приём партнёрских заказов, восстановить обработчики и затем разобрать очередь.
- **RabbitMQ in-flight:** предупреждение, если in-flight выше согласованной ёмкости consumers более 10 минут; начальный ориентир — более 100 сообщений на consumer. Критический алерт — отсутствие ack 5 минут при ненулевом in-flight. Действия: проверить зависшие обработчики, таймауты и prefetch, не подтверждать сообщения до успешного сохранения результата.
- **RabbitMQ DLX:** критический алерт при появлении хотя бы одного нового сообщения, поскольку оно может соответствовать потерянному заказу. Действия: создать инцидент, сохранить причину, после исправления безопасно переотправить сообщение. Автоматическое бесконечное повторение запрещено.
- **RabbitMQ redelivery:** предупреждение, если доля повторных доставок выше 1% за 10 минут; критический алерт выше 5% за 5 минут. Действия: проверить ошибки consumers, идемпотентность и цикл повторов.
- **RabbitMQ consumers:** критический алерт, если число consumers стало нулём при наличии ready-сообщений дольше 1 минуты. Действия: перезапустить или восстановить consumer, проверить соединение и релиз.
- **S3:** предупреждение при доле ошибок выше 1% за 10 минут, критический алерт выше 5% за 5 минут; предупреждение, если p95 операции выше 2 секунд 10 минут. По размеру — тикет при отклонении недельного роста более чем в два раза от базовой линии. Действия: проверить доступ, квоты, сеть и политику жизненного цикла.
- **Расчёт цены:** предупреждение, если p95 выше 30 минут за час или старейшая ожидающая задача старше 10 минут; критический алерт, если отдельный расчёт длится более 45 минут либо нет завершённых расчётов 15 минут при непустой очереди. Действия: проверить очередь и процесс MES, уведомить поддержку, не терять задачу, после восстановления продолжить обработку идемпотентно.
- **Заказы в статусах:** для `SUBMITTED` предупреждение при отсутствии `PRICE_CALCULATED` более 30 минут, критический алерт более 45 минут; для остальных статусов начальные пороги задаются владельцем процесса, а общий критический порог — невозможность завершить заказ за обещанные 21 день. Действия: автоматически создать тикет с идентификаторами заказов в защищённой системе, уведомить поддержку и владельца этапа, проверить RabbitMQ и соответствующий сервис.
- **Отсутствие данных мониторинга:** критический алерт, если метрики любого единственного экземпляра не поступают более 2 минут. Действия: проверить сам сервис, exporter и канал доставки метрик. Отсутствие данных нельзя считать нормальным нулевым значением.

Уведомления предупреждающего уровня направляются в рабочий канал команды и создают тикет, если проблема сохраняется. Критические алерты поступают дежурному инженеру через push или звонок и создают инцидент. Для каждого алерта должна быть короткая инструкция: что проверить, кто владелец компонента и как безопасно снизить влияние на клиентов.

# План действий

1. Согласовать с разработчиками и бизнесом названия сервисов, маршрутов, очередей, статусов, владельцев компонентов, цели по времени ответа и допустимое время каждого этапа заказа.
2. Развернуть в production отказоустойчивое хранилище временных рядов на базе Prometheus или совместимого управляемого решения. Настроить сроки хранения и оценить объём данных с учётом кардинальности.
3. Развернуть Grafana, подключить источник метрик и настроить ролевой доступ. Технические дашборды доступны инженерной команде, бизнес-дашборд по срокам заказов — продакт-менеджеру и поддержке.
4. Инструментировать Java-приложения Shop API и CRM API через Micrometer, C# MES API через OpenTelemetry Metrics или .NET Meter. Добавить RED-метрики, пулы потоков, соединения с БД и метрики фонового расчёта.
5. Установить инфраструктурные exporters или включить метрики облачного провайдера для виртуальных машин и управляемых PostgreSQL. Собрать CPU, память, диск, I/O, соединения, блокировки и задержки запросов.
6. Подключить RabbitMQ exporter и настроить метрики ready, in-flight, DLX, redelivery, consumers, publish, ack и возраста старейшего сообщения. Проверить, что все рабочие очереди имеют DLX и ограниченную политику повторов.
7. Подключить метрики S3: размер, число объектов, ошибки и latency операций. Проверить политики хранения и жизненного цикла файлов.
8. Добавить бизнес-метрики при каждом переходе заказа между статусами. Для текущего возраста заказов выполнять периодическую агрегацию из БД, не создавая отдельный временной ряд на каждый заказ.
9. Создать дашборды: обзор системы; RED по каждому API; USE по экземплярам и БД; RabbitMQ; S3; расчёт цены; воронка заказов и время в статусах. На MES-дашборде сопоставить HTTP latency с запросами PostgreSQL.
10. Настроить Alertmanager или аналог: маршрутизацию предупреждений и критических алертов, группировку, подавление дублей, график дежурств и инструкции по реагированию.
11. Провести нагрузочную проверку партнёрского API и сквозного оформления заказа. Проверить, что дашборды отражают нагрузку, а тестовые сбои consumer, БД и S3 вызывают ожидаемые алерты.
12. Собирать базовую линию две-четыре недели, затем уточнить пороги, SLO и допустимое время в статусах. Ежемесячно пересматривать ёмкость, ложные срабатывания и прогноз роста.
